# CogMemory AD / 智忆评前端设计基线

## 1. 文档定位

本文档是 CogMemory AD / 智忆评前端视觉风格、交互气质、页面布局和组件表现的长期基线，用于约束后续前端页面、组件、布局、样式和交互迁移。

- 本文档约束后续 `frontend\app`、`frontend\src`、页面、组件、布局、样式和交互迁移。
- 后续从 ReviewX 迁移前端公共结构时，必须先阅读本文档。
- 本项目只继承 ReviewX 的工程结构、配置经验和组件治理方法，不继承 ReviewX 的视觉风格。
- 后续前端页面与组件设计必须以本文档作为设计边界。
- 当前前端已形成 Auth、Patients、Assessments、ClinicalReport 与 B17 历史 / 趋势产品页面，并使用 Tailwind CSS 与既有 `Button`、`Card`、`Badge` UI components。
- 本设计基线不冻结具体 token、class 或组件实现；当前工程结构、组件和页面事实以 frontend snapshot、component map 与实际代码为准。
- 上述当前实现仍不代表一期完整产品或完整设计系统全部完成。

## 2. 产品气质

CogMemory AD 前端气质为：

- 医疗系统
- 临床评估
- 低干扰
- 高可读性
- 冷静可信

用户主要是医生、评估人员、机构管理人员和参与认知评估的患者。页面目标是提升评估、记录、报告和医生工作流效率，不追求互联网营销感、炫酷感或重装饰感。

## 3. 视觉方向

CogMemory AD 更适合：

- 浅色背景
- 低饱和蓝绿
- 清晰分区
- 大字号可读
- 少动画
- 少装饰
- 稳定、克制、可信的医疗系统界面

## 4. 色彩原则

- 主色建议使用低饱和蓝绿。
- 背景以浅色为主。
- 大面积背景避免高饱和紫、橙、红。
- 警示色只用于异常、风险、错误、重要提醒。
- 不使用强营销感渐变作为主要视觉语言。
- 色彩必须服务于阅读、分区和状态识别。
- 当前使用 Tailwind CSS 与既有 UI components；本文档只约束长期视觉原则，不定义或冻结具体 Tailwind token、class 和组件实现。

## 5. 布局原则

- 清晰分区。
- 信息层级明确。
- 医生工作流优先。
- 页面结构应围绕“评估、记录、报告、医生工作流”组织。
- 不堆叠过多卡片。
- 不使用复杂装饰性布局。
- 避免让视觉效果压过临床信息。

## 5.1 响应式与设备兼容基线

设计支持范围与代表性 CSS content viewport 如下；所有尺寸均指实际 `window.innerWidth × window.innerHeight`：

| 设备范围 | 代表性 viewport |
|---|---|
| 手机竖屏 | `390×844` |
| 大屏 Android 平板竖屏 | `800×1280` |
| 大屏 Android 平板横屏 | `1280×800` |
| 大屏 iPad 竖屏 | `1024×1366` |
| 大屏 iPad 横屏 | `1366×1024` |
| 紧凑桌面 | `1280×720` |
| 桌面大屏 | `1536×864` |

- 页面不得产生 document / main 全局横向溢出；Grid、Flex 和 Card 子项必须允许合理收缩。
- 宽表格允许在明确的局部容器中横向滚动，但不得撑宽整个页面。
- 多栏布局在窄屏下应自然收缩或切换为单列。
- Dialog、表单、主要按钮和错误提示必须保持可见、可聚焦、可操作。
- 图片、媒体证据、Canvas、连线、绘图和手写区域必须在大屏平板横竖屏下保持可用。
- 横竖屏或 viewport 变化不得静默丢失仍在 React 内存中的合法未提交草稿。
- 手机和平板不是桌面页面的简单缩小版；核心评估流程与医生操作流程必须完整可用。

## 6. 字号与可读性

- 评估题目、患者信息、报告摘要、医生操作入口必须具备高可读性。
- 表格、表单、量表项需要足够行距。
- 避免小字号密集堆叠。
- 关键信息应优先可读，而不是优先节省空间。
- 患者端页面尤其要考虑老年用户或认知能力下降用户的阅读负担。

## 7. 交互与动效

- 少动画。
- 少复杂转场。
- 交互反馈要清楚、稳定、可预期。
- 不使用炫酷动效制造“科技感”。
- 医生端优先效率。
- 患者端优先理解和低压力。

## 8. 装饰与视觉噪音控制

- 少装饰。
- 少大面积插画。
- 少强阴影。
- 少复杂渐变。
- 不使用娱乐化视觉元素。
- 不使用过度 SaaS 化的营销 Banner。
- 临床评估页面应保持克制、稳定、专注。

## 9. 信息重点

页面设计优先突出：

- 评估
- 记录
- 报告
- 医生工作流
- 患者认知评估状态
- 临床可追溯信息
- 评估进度
- 风险提示
- 报告生成与查看

## 10. 医生端设计基线

- 医生端强调工作效率、数据清晰、结果可追溯。
- 应优先支持快速查看患者、发起评估、查看记录、生成报告。
- 表格和详情页要清楚分区。
- 操作按钮要稳定、明确、低干扰。
- 不使用花哨视觉抢占医生注意力。

## 11. 患者端设计基线

- 患者端强调低压力、易理解、大字号、简单操作。
- 量表作答页面应减少无关信息。
- 每一步操作要明确。
- 题目、选项、图片题和进度状态必须清楚。
- 不制造紧张、游戏化或娱乐化体验。

## 12. 报告与评估结果设计基线

- 报告页面优先清晰、可读、可追溯。
- 评估结果不能用夸张颜色制造诊断暗示。
- 风险提示必须克制、准确、可解释。
- 不把系统结果写成最终医疗诊断。
- 报告视觉应适合医生查看、打印或导出。

## 13. 与 ReviewX 的关系

- ReviewX 仅作为工程结构、配置经验和组件治理方法参考。
- 不继承 ReviewX 的视觉风格。
- 不继承 ReviewX 的颜色体系。
- 不继承 ReviewX 的页面布局。
- 不继承 ReviewX 的业务文案。
- 不继承 ReviewX 的项目评审管理后台气质。
- CogMemory AD 与 ReviewX 必须保持前端视觉隔离。
- 后续迁移 ReviewX 前端 `app` / `src` 时，必须按 CogMemory AD 设计基线重构视觉表现。

## 14. 禁止事项

- 不照搬 ReviewX 页面视觉。
- 不照搬 ReviewX 管理后台气质。
- 不使用高饱和大面积装饰色。
- 不使用强营销感视觉。
- 不用动画替代清晰信息结构。
- 不让装饰影响评估题目、患者信息、报告结果的阅读。
- 不在 UI 中展示真实患者隐私样本。
- 不把评估结果设计成最终诊断结论。

## 15. 后续维护规则

- 新增页面、组件、布局、样式前，应先检查本文档。
- 当前已实现页面与组件继续遵循本文档；具体实现事实由 frontend snapshot、component map 与代码维护。
- 如后续实际产品风格调整，应先更新本文档，再改页面和组件。
- `handoff-frontend-component-map.md`、`handoff-frontend-route-map.md`、`handoff-frontend-testing-playbook.md` 应与本文档保持一致。
- 七个正式 viewport 若调整，必须同步更新 `handoff-frontend-testing-playbook.md`。
- 本设计基线定义“必须适配什么”，`handoff-frontend-testing-playbook.md` 定义“如何验证”；测试执行、结果判定和证据归档细节只在 testing playbook 维护。
- Codex 后续执行前端页面或组件迁移任务时，必须把本文档作为视觉基线。
