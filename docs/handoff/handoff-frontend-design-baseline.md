# CogMemory AD / 智忆评前端设计基线

## 1. 文档定位

本文档是 CogMemory AD / 智忆评前端视觉风格、交互气质、页面布局和组件表现的长期基线，用于约束后续前端页面、组件、布局、样式和交互迁移。

- 本文档约束后续 `frontend\app`、`frontend\src`、页面、组件、布局、样式和交互迁移。
- 后续从 ReviewX 迁移前端公共结构时，必须先阅读本文档。
- 本项目只继承 ReviewX 的工程结构、配置经验和组件治理方法，不继承 ReviewX 的视觉风格。
- 后续前端页面与组件设计必须以本文档作为设计边界。
- 当前前端已形成 Auth、Patients、Assessments、ClinicalReport 与 B17 历史 / 趋势产品页面，并使用 Tailwind CSS 与既有 `Button`、`Card`、`Badge` UI components。
- 本设计基线不冻结具体 token、class 或组件实现；当前工程结构、组件和页面事实以 frontend snapshot、component map 与实际代码为准。
- 上述当前实现仍不代表一期完整产品或完整设计系统全部完成。

## 2. 产品气质

CogMemory AD 前端气质为：

- 医疗系统
- 临床评估
- 低干扰
- 高可读性
- 冷静可信

用户主要是医生、评估人员、机构管理人员和参与认知评估的患者。页面目标是提升评估、记录、报告和医生工作流效率，不追求互联网营销感、炫酷感或重装饰感。

## 3. 视觉方向

CogMemory AD 更适合：

- 浅色背景
- 低饱和蓝绿
- 清晰分区
- 大字号可读
- 少动画
- 少装饰
- 稳定、克制、可信的医疗系统界面

## 4. 色彩原则

- 主色建议使用低饱和蓝绿。
- 背景以浅色为主。
- 大面积背景避免高饱和紫、橙、红。
- 警示色只用于异常、风险、错误、重要提醒。
- 不使用强营销感渐变作为主要视觉语言。
- 色彩必须服务于阅读、分区和状态识别。
- 当前使用 Tailwind CSS 与既有 UI components；本文档只约束长期视觉原则，不定义或冻结具体 Tailwind token、class 和组件实现。

## 5. 布局原则

- 清晰分区。
- 信息层级明确。
- 临床工作流优先。
- 页面结构应围绕“患者施测、医护记录、医生复核、报告和临床运营”组织。
- 不堆叠过多卡片。
- 不使用复杂装饰性布局。
- 避免让视觉效果压过临床信息。

## 5.1 响应式与设备兼容基线

设计支持范围与代表性 CSS content viewport 如下；所有尺寸均指实际 `window.innerWidth × window.innerHeight`：

| 设备范围 | 代表性 viewport |
|---|---|
| 手机竖屏 | `390×844` |
| 大屏 Android 平板竖屏 | `800×1280` |
| 大屏 Android 平板横屏 | `1280×800` |
| 大屏 iPad 竖屏 | `1024×1366` |
| 大屏 iPad 横屏 | `1366×1024` |
| 紧凑桌面 | `1280×720` |
| 桌面大屏 | `1536×864` |

- 页面不得产生 document / main 全局横向溢出；Grid、Flex 和 Card 子项必须允许合理收缩。
- 宽表格允许在明确的局部容器中横向滚动，但不得撑宽整个页面。
- 多栏布局在窄屏下应自然收缩或切换为单列。
- Dialog、表单、主要按钮和错误提示必须保持可见、可聚焦、可操作。
- 图片、媒体证据、Canvas、连线、绘图和手写区域必须在大屏平板横竖屏下保持可用。
- 横竖屏或 viewport 变化不得静默丢失仍在 React 内存中的合法未提交草稿。
- 患者角色和医护角色都必须响应式支持上述既定手机、平板和桌面代表 viewport；不得根据“手机 / 平板 / 电脑”或屏幕尺寸决定角色。设备是否具备某一步骤所需的触控、麦克风或其他硬件能力，按该步骤合同判断，不改变页面的响应式责任。
- 双设备屏幕条件不一致时，通常优先将更大、更适合阅读和触控的设备交给患者；医护端通常可以容忍较小屏幕，但核心准备、观察、异常控制和复核操作仍必须可用。患者端与医护端的实际角色由安全会话和业务流程决定，不由屏幕大小推断。
- 不要求所有设备像素级一致，也不穷举所有设备 × 角色组合；继续使用上述七个代表性 viewport 验证响应式合同，不新增 breakpoint 或 viewport 数量。

## 6. 字号与可读性

- 评估题目、患者信息、报告摘要、医生操作入口必须具备高可读性。
- 表格、表单、量表项需要足够行距。
- 避免小字号密集堆叠。
- 关键信息应优先可读，而不是优先节省空间。
- 患者端页面尤其要考虑老年用户或认知能力下降用户的阅读负担。

## 7. 交互与动效

- 少动画。
- 少复杂转场。
- 交互反馈要清楚、稳定、可预期。
- 不使用炫酷动效制造“科技感”。
- 临床工作端优先效率、异常可见和低操作负担。
- 患者施测终端优先理解、低压力和安全交接。

## 8. 装饰与视觉噪音控制

- 少装饰。
- 少大面积插画。
- 少强阴影。
- 少复杂渐变。
- 不使用娱乐化视觉元素。
- 不使用过度 SaaS 化的营销 Banner。
- 临床评估页面应保持克制、稳定、专注。

## 9. 信息重点

页面设计优先突出：

- 评估
- 记录
- 报告
- 医生工作流
- 患者认知评估状态
- 临床可追溯信息
- 评估进度
- 风险提示
- 报告生成与查看

## 10. 核心逻辑工作区与临床工作端设计基线

- 一期采用患者施测终端、临床工作端、临床运营与系统管理工作区三个逻辑工作区；它们可以复用同一前端应用、布局和工作流，不等于三套独立应用、微前端或强制角色分拆。知情者辅助信息采集不是第四套应用。
- 临床工作端在同一工作流内区分医护施测模式与量表作答复核。医生可以同时承担两种职责，不强制两个账号或互斥角色；WP-10 患者施测与医患职责以当前 patient-administration contract 为准，WP-12 只锁定仍未确定的运营与管理职责，不重新打开 WP-10.0。
- 医护施测模式优先支持患者 / 访视 / 量表选择、必要设备准备、按 `ScaleVersion` 与当前呈现资产合同使用既定施测语言、同设备交接或跨设备安全进入、当前步骤 / 进度 / 求助查看、动作观察、异常和影响因素记录，以及暂停、接管、纠正、恢复和终止；准备页不新增语言选择状态或 DTO。
- 正常受监督患者施测由患者端连续推进题目主链；医护现实观察不要求逐题同步系统写入。双设备是患者端与医护端的角色分工，不等于双方并发写同一 Session；异常时才使用暂停、接管、重做、technical replay、重签或终止等控制能力。
- 影响因素采用结构化分类加必要补充说明的低负担呈现，至少能够覆盖感官、手部操作、语言 / 文化 / 教育、指令理解、疲劳 / 情绪 / 拒绝、环境、设备 / 网络和其他临床原因；本文不冻结枚举、字段或组件。
- 量表作答复核采用“正常复核优先，重点项目适度提示”：先呈现整份量表的正常复核结构，再对适用语音步骤的录音与转写候选、书写绘图、医护观察、控制事实、缺失 / 不一致、影响因素和无法完成原因提供标记、分组或按需展开。简单客观项目可以汇总呈现并支持快速逐项复核，但正式草稿仍逐题复用既有 A14 PATCH，readiness 后仍由 A16 显式整体提交；不形成 batch confirm 写协议，也不新增 `reviewed`、`confirmed`、`reviewCompleted`、`doctorConfirmed`、`reviewRevision` 等第二套持久确认状态。
- 医生必须能展开查看必要事实。正常首次复核形成现有 `ItemResponse` 草稿时，不强制填写无业务价值的修改原因或 `operatorNote`；对已有草稿作实质纠正、与原始证据存在需要解释的明显差异、临床判断确需解释或既有合同要求时，记录必要说明。既有审计与 submission 留痕继续保留，最终进入提交、评分和报告链前仍须显式整体确认；不新增 reason 字段、必填 UI 或确认状态。
- 临床运营与系统管理工作区继续使用最低充分页面或受控工具承载账号运营、患者 / 访视维护、临床任务入口、异常会话、报告输出和作废，不建设统计型 Dashboard 或复杂管理平台。
- 知情者信息由医护在患者或访视上下文中代录时，应清楚标识“来源：知情者”及关系、接触频率或了解程度等必要背景，并与患者作答、ItemResponse、量表得分和医生结论分区呈现；不要求知情者独立登录或家庭门户。

## 11. 患者施测终端设计基线

- 患者施测终端强调低压力、易理解、大字号、简单操作和隐私安全；采用一步一屏，每屏只有一个明确的主要操作。
- 使用大触控区、足够间距和尽量无需滚动的布局；手机、平板、触控一体机、触控显示器和桌面代表 viewport 都遵循同一低负担与响应式原则。特定题目需要的真实触控、麦克风或其他硬件能力另按步骤合同验收，不得把角色绑定到设备尺寸。
- 明确显示正在播放、正在录音、正在上传、等待医护和已完成等状态；只有步骤规则允许时才显示重播按钮。
- 始终提供清楚、容易触达的“请医护人员帮助”入口。患者不得自行跳题，除非步骤合同明确允许；不得以自动快速切题牺牲患者理解或医护观察。
- 不使用复杂导航、表格、密集表单、游戏化积分、答案提示或诊断暗示，不展示分数、报告、医生意见和其他患者信息。
- 患者施测终端应根据施测步骤语音播报当前题目内容和施测指导语。每个步骤分别确定文字是否显示、是否播报、自动播放或患者主动播放、是否允许重播、重播次数或条件、播放完成前能否作答，以及中断和失败处置；不得使用一个全局规则控制全部步骤。
- MMSE / MoCA 正式患者施测中的正式题目内容、正式施测指导语及影响测量条件的语音刺激，凡按步骤合同需要语音呈现，均使用与 `ScaleVersion` / step 绑定、版本化且经人工确认的固定音频资产；正式施测不得针对上述内容调用运行时 TTS。文字显示必须服从题目规则，视觉任务只播报必要指导且不得泄露答案；禁止把页面全部文本无差别朗读。
- 正式测量内容与普通操作 / 状态提示必须分层。“正在上传”“请稍候”“请医护人员帮助”等普通 UI 提示不属于正式测量刺激，继续按现有 UI 合同呈现；本文不为其另行设计或强制使用 TTS，也不新增 Runtime TTS provider、fallback、cache、timeout、provider retry、TTS 配置或新音频资产类型。
- 正式施测前提供最低充分的准备：`screen`、`input`、`sound`、`microphone` 四项必要设备检查共同决定 `ready`，四项完成后才可进入正式施测；触摸 / 书写等不计分设备操作练习推荐给不熟悉设备的患者按需使用，熟悉设备者可以跳过，练习不参与 `ready`。一期施测语言由 `ScaleVersion` 与当前呈现资产合同决定，准备页不通过额外 checkbox 选择或改变语言。练习不得进入 `ItemResponse`、`MediaEvidence`、评分、报告或正式 timing / playback 事实。
- 同设备从医护工作模式进入患者模式后，staff Session 失效，后退、刷新、历史记录和普通导航均不得进入临床工作端；患者模式只显示当前施测所需的最少身份信息。完成、终止或超时后清除患者可见内容，结束页只提示完成并要求交还设备；返回临床工作端需要医护 / 医生重新认证。重新认证是有意接受的简单安全边界，不为减少一次登录设计同浏览器双身份保持、隐藏身份或自动恢复。

## 12. 报告与评估结果设计基线

- 报告页面优先清晰、可读、可追溯。
- 评估结果不能用夸张颜色制造诊断暗示。
- 风险提示必须克制、准确、可解释。
- 不把系统结果写成最终医疗诊断。
- 报告视觉应适合医生查看、打印或导出。

## 13. 与 ReviewX 的关系

- ReviewX 仅作为工程结构、配置经验和组件治理方法参考。
- 不继承 ReviewX 的视觉风格。
- 不继承 ReviewX 的颜色体系。
- 不继承 ReviewX 的页面布局。
- 不继承 ReviewX 的业务文案。
- 不继承 ReviewX 的项目评审管理后台气质。
- CogMemory AD 与 ReviewX 必须保持前端视觉隔离。
- 后续迁移 ReviewX 前端 `app` / `src` 时，必须按 CogMemory AD 设计基线重构视觉表现。

## 14. 禁止事项

- 不照搬 ReviewX 页面视觉。
- 不照搬 ReviewX 管理后台气质。
- 不使用高饱和大面积装饰色。
- 不使用强营销感视觉。
- 不用动画替代清晰信息结构。
- 不让装饰影响评估题目、患者信息、报告结果的阅读。
- 不在 UI 中展示真实患者隐私样本。
- 不把评估结果设计成最终诊断结论。

## 15. 后续维护规则

- 新增页面、组件、布局、样式前，应先检查本文档。
- 当前已实现页面与组件继续遵循本文档；具体实现事实由 frontend snapshot、component map 与代码维护。
- 如后续实际产品风格调整，应先更新本文档，再改页面和组件。
- `handoff-frontend-component-map.md`、`handoff-frontend-route-map.md`、`handoff-frontend-testing-playbook.md` 应与本文档保持一致。
- 七个正式 viewport 若调整，必须同步更新 `handoff-frontend-testing-playbook.md`。
- 本设计基线定义“必须适配什么”，`handoff-frontend-testing-playbook.md` 定义“如何验证”；测试执行、结果判定和证据归档细节只在 testing playbook 维护。
- Codex 后续执行前端页面或组件迁移任务时，必须把本文档作为视觉基线。
