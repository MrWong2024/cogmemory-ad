# CogMemory AD / 智忆评前端设计基线

## 1. 文档定位

本文档是 CogMemory AD / 智忆评前端视觉风格、交互气质、页面布局和组件表现的长期基线，用于约束后续前端页面、组件、布局、样式和交互迁移。

- 本文档约束后续 `frontend\app`、`frontend\src`、页面、组件、布局、样式和交互迁移。
- 后续从 ReviewX 迁移前端公共结构时，必须先阅读本文档。
- 本项目只继承 ReviewX 的工程结构、配置经验和组件治理方法，不继承 ReviewX 的视觉风格。
- 后续前端页面与组件设计必须以本文档作为设计边界。
- 当前前端已形成 Auth、Patients、Assessments、ClinicalReport 与 B17 历史 / 趋势产品页面，并使用 Tailwind CSS 与既有 `Button`、`Card`、`Badge` UI components。
- 本设计基线不冻结具体 token、class 或组件实现；当前工程结构、组件和页面事实以 frontend snapshot、component map 与实际代码为准。
- 受监督患者施测的 same/cross、准备、逐题、媒体、播放、安全会话、异常控制与 F2/F3 详细业务合同统一见 [Patient Administration Contract](./handoff-patient-administration-contract.md)，本文只维护其设计投影。
- 上述当前实现仍不代表一期完整产品或完整设计系统全部完成。

## 2. 产品气质

CogMemory AD 前端气质为：

- 医疗系统
- 临床评估
- 低干扰
- 高可读性
- 冷静可信

用户主要是医生、评估人员、机构管理人员和参与认知评估的患者。页面目标是提升评估、记录、报告和医生工作流效率，不追求互联网营销感、炫酷感或重装饰感。

## 3. 视觉方向

CogMemory AD 更适合：

- 浅色背景
- 低饱和蓝绿
- 清晰分区
- 大字号可读
- 少动画
- 少装饰
- 稳定、克制、可信的医疗系统界面

## 4. 色彩原则

- 主色建议使用低饱和蓝绿。
- 背景以浅色为主。
- 大面积背景避免高饱和紫、橙、红。
- 警示色只用于异常、风险、错误、重要提醒。
- 不使用强营销感渐变作为主要视觉语言。
- 色彩必须服务于阅读、分区和状态识别。
- 当前使用 Tailwind CSS 与既有 UI components；本文档只约束长期视觉原则，不定义或冻结具体 Tailwind token、class 和组件实现。

## 5. 布局原则

- 清晰分区。
- 信息层级明确。
- 临床工作流优先。
- 页面结构应围绕“患者施测、医护记录、医生复核、报告和临床运营”组织。
- 不堆叠过多卡片。
- 不使用复杂装饰性布局。
- 避免让视觉效果压过临床信息。

## 5.1 响应式与设备兼容基线

设计支持范围与代表性 CSS content viewport 如下；所有尺寸均指实际 `window.innerWidth × window.innerHeight`：

| 设备范围 | 代表性 viewport |
|---|---|
| 手机竖屏 | `390×844` |
| 大屏 Android 平板竖屏 | `800×1280` |
| 大屏 Android 平板横屏 | `1280×800` |
| 大屏 iPad 竖屏 | `1024×1366` |
| 大屏 iPad 横屏 | `1366×1024` |
| 紧凑桌面 | `1280×720` |
| 桌面大屏 | `1536×864` |

- 页面不得产生 document / main 全局横向溢出；Grid、Flex 和 Card 子项必须允许合理收缩。
- 宽表格允许在明确的局部容器中横向滚动，但不得撑宽整个页面。
- 多栏布局在窄屏下应自然收缩或切换为单列。
- Dialog、表单、主要按钮和错误提示必须保持可见、可聚焦、可操作。
- 图片、媒体证据、Canvas、连线、绘图和手写区域必须在大屏平板横竖屏下保持可用。
- 横竖屏或 viewport 变化不得静默丢失仍在 React 内存中的合法未提交草稿。
- 患者角色和医护角色都必须响应式支持上述既定手机、平板和桌面代表 viewport；不得根据“手机 / 平板 / 电脑”或屏幕尺寸决定角色。设备是否具备某一步骤所需的触控、麦克风或其他硬件能力，按该步骤合同判断，不改变页面的响应式责任。
- 双设备屏幕条件不一致时，通常优先将更大、更适合阅读和触控的设备交给患者；医护端通常可以容忍较小屏幕，但核心准备、观察、异常控制和复核操作仍必须可用。患者端与医护端的实际角色由安全会话和业务流程决定，不由屏幕大小推断。
- 不要求所有设备像素级一致，也不穷举所有设备 × 角色组合；继续使用上述七个代表性 viewport 验证响应式合同，不新增 breakpoint 或 viewport 数量。

## 6. 字号与可读性

- 评估题目、患者信息、报告摘要、医生操作入口必须具备高可读性。
- 表格、表单、量表项需要足够行距。
- 避免小字号密集堆叠。
- 关键信息应优先可读，而不是优先节省空间。
- 患者端页面尤其要考虑老年用户或认知能力下降用户的阅读负担。

## 7. 交互与动效

- 少动画。
- 少复杂转场。
- 交互反馈要清楚、稳定、可预期。
- 不使用炫酷动效制造“科技感”。
- 临床工作端优先效率、异常可见和低操作负担。
- 患者施测终端优先理解、低压力和安全交接。

## 8. 装饰与视觉噪音控制

- 少装饰。
- 少大面积插画。
- 少强阴影。
- 少复杂渐变。
- 不使用娱乐化视觉元素。
- 不使用过度 SaaS 化的营销 Banner。
- 临床评估页面应保持克制、稳定、专注。

## 9. 信息重点

页面设计优先突出：

- 评估
- 记录
- 报告
- 医生工作流
- 患者认知评估状态
- 临床可追溯信息
- 评估进度
- 风险提示
- 报告生成与查看

## 10. 核心逻辑工作区与临床工作端设计基线

- 一期采用患者施测终端、临床工作端、临床运营与系统管理工作区三个逻辑工作区；它们可以复用同一前端应用、布局和工作流，不等于三套独立应用、微前端或强制角色分拆。知情者辅助信息采集不是第四套应用。
- 临床工作端优先效率、异常可见和低操作负担；医生可以同时承担施测与复核职责，业务职责不自动等于互斥账号、新技术角色或独立应用。
- 量表作答复核遵循“正常复核优先，重点项目适度提示”：先提供整份量表的清晰复核结构，再对确有事实的缺失、不一致、原始证据、影响因素或异常进行适度标记和按需展开。
- 医护必须能展开查看完成专业判断所需的患者原始事实与既有临床记录；界面不要求为正常项目填写形式性说明，也不以额外 UI 状态替代正式业务链。
- 临床运营与系统管理工作区使用最低充分页面或受控工具，不建设统计型 Dashboard 或复杂管理平台。
- 知情者信息由医护代录时，应清楚标识来源及必要背景，并与患者作答、正式 ItemResponse、量表得分和医生结论分区呈现；不要求知情者独立登录或家庭门户。
- 受监督患者施测的准备、same/cross、安全控制、复核和正式提交边界服从 [Patient Administration Contract](./handoff-patient-administration-contract.md)；本节不维护字段、状态机、角色枚举或写协议。

## 11. 患者施测终端设计基线

- 患者施测终端强调低压力、易理解、大字号、简单操作和隐私安全；采用一步一屏，每屏只有一个明确的主要操作。
- 使用大触控区、足够间距和尽量无需滚动的布局；手机、平板、触控一体机、触控显示器和桌面代表 viewport 都遵循同一低负担与响应式原则。
- 明确呈现播放、录音、上传、等待医护、已完成和失败等用户需要理解的状态；反馈必须使用文字或语义，不只依赖颜色。
- 始终提供清楚、容易触达的“请医护人员帮助”入口；不使用复杂导航、密集表格、游戏化积分或增加认知负担的交互。
- 不展示评分、报告、诊断暗示、医生意见、其他患者信息或完成当前步骤不需要的身份信息；共享设备上的患者信息保持最小化。
- 视觉任务不得泄露答案，媒体呈现必须服从步骤合同；设计层只确保媒体可理解、可操作且不会被布局破坏，不在此定义逐 step 播放、重播或录音规则。
- 真实触控、麦克风、横竖屏和其他步骤所需硬件能力应在目标设备上验收；页面响应式支持不等于真实设备合同已经通过。
- same/cross、安全会话、准备检查、固定媒体、逐题呈现、播放和安全退出的详细规则统一见 [Patient Administration Contract](./handoff-patient-administration-contract.md)。

## 12. 报告与评估结果设计基线

- 报告页面优先清晰、可读、可追溯。
- 评估结果不能用夸张颜色制造诊断暗示。
- 风险提示必须克制、准确、可解释。
- 不把系统结果写成最终医疗诊断。
- 报告视觉应适合医生查看、打印或导出。

## 12.1 用户可见文案基线

- 正常业务 UI 必须使用对应角色能够理解的业务语言，不直接暴露内部实现术语、字段名、raw enum、阶段编号或技术机制。
- `A# / B# / WP#`、`scope`、`reportVersion`、`updatedAt / lockedAt`、`revision / CAS`、`DTO / Schema / API / HTTP`、`Mongo / OSS` 以及 raw status / code / internal id 等仅作为内部信息类别示例，不构成需要维护的穷举黑名单。
- 用户确需理解某个内部状态时，应先转译为业务含义，例如将 `session_conflict` 表达为“状态已变化，需要重新确认”，将 `replacement` 表达为“更正版本”；本文不维护完整映射表，也不规定固定中文措辞。
- 具有审计或排障价值、但普通用户无需理解的内部事实不得失真或删除；应降低默认视觉优先级，必要时放入默认收起的“技术与审计信息”等区域。
- 患者端从严：只呈现完成当前步骤所需的信息、状态和动作，不要求患者理解 Session、Evidence、revision、保存协议等系统实现概念。
- 医护端可以展示专业临床术语，但不得把工程实现语言包装或伪装成临床术语。
- Codex 新增或修改用户可见文案时，完成前只对本次实际改动做最低充分检查：是否直接暴露内部实现语言；如有，应改为业务化表达，或说明其确有用户可见价值。本规则不触发对全站既有文案的机械扫描或治理。

## 13. 与 ReviewX 的关系

- ReviewX 仅作为工程结构、配置经验和组件治理方法参考。
- 不继承 ReviewX 的视觉风格。
- 不继承 ReviewX 的颜色体系。
- 不继承 ReviewX 的页面布局。
- 不继承 ReviewX 的业务文案。
- 不继承 ReviewX 的项目评审管理后台气质。
- CogMemory AD 与 ReviewX 必须保持前端视觉隔离。
- 后续迁移 ReviewX 前端 `app` / `src` 时，必须按 CogMemory AD 设计基线重构视觉表现。

## 14. 禁止事项

- 不照搬 ReviewX 页面视觉。
- 不照搬 ReviewX 管理后台气质。
- 不使用高饱和大面积装饰色。
- 不使用强营销感视觉。
- 不用动画替代清晰信息结构。
- 不让装饰影响评估题目、患者信息、报告结果的阅读。
- 不在 UI 中展示真实患者隐私样本。
- 不把评估结果设计成最终诊断结论。

## 15. 后续维护规则

- 新增页面、组件、布局或样式前先检查本文档；视觉、布局、交互气质和长期 UX 原则变化时更新本设计基线。
- 当前工程、route、component、API 与测试事实分别由 snapshot、maps、current code 和 testing playbook 维护；本文只在设计投影受影响时同步。
- 患者施测详细业务合同只更新 Patient Administration Contract，本设计基线只保留实现 UX 原则所需的最低摘要与引用。
- 七个正式 viewport 若调整，应同步检查 testing playbook 的验证设计；测试执行、结果和 evidence 仍只由 testing playbook 维护。
- 遵循 reference, don't restate；“同步相关文档”只更新职责确实变化的 owner / projection，没有设计职责变化时本文件保持 zero diff。
- Codex 执行前端页面或组件迁移任务时，必须把本文档作为视觉基线。
