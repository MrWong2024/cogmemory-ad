# CogMemory AD / 智忆评前端设计基线

## 1. 文档定位

本文档是 CogMemory AD / 智忆评前端视觉风格、交互气质、页面布局和组件表现的长期基线，用于约束后续前端页面、组件、布局、样式和交互迁移。

- 本文档约束后续 `frontend\app`、`frontend\src`、页面、组件、布局、样式和交互迁移。
- 后续从 ReviewX 迁移前端公共结构时，必须先阅读本文档。
- 本项目只继承 ReviewX 的工程结构、配置经验和组件治理方法，不继承 ReviewX 的视觉风格。
- 后续前端页面与组件设计必须以本文档作为设计边界。
- 当前前端已形成 Auth、Patients、Assessments、ClinicalReport 与 B17 历史 / 趋势产品页面，并使用 Tailwind CSS 与既有 `Button`、`Card`、`Badge` UI components。
- 本设计基线不冻结具体 token、class 或组件实现；当前工程结构、组件和页面事实以 frontend snapshot、component map 与实际代码为准。
- 上述当前实现仍不代表一期完整产品或完整设计系统全部完成。

## 2. 产品气质

CogMemory AD 前端气质为：

- 医疗系统
- 临床评估
- 低干扰
- 高可读性
- 冷静可信

用户主要是医生、评估人员、机构管理人员和参与认知评估的患者。页面目标是提升评估、记录、报告和医生工作流效率，不追求互联网营销感、炫酷感或重装饰感。

## 3. 视觉方向

CogMemory AD 更适合：

- 浅色背景
- 低饱和蓝绿
- 清晰分区
- 大字号可读
- 少动画
- 少装饰
- 稳定、克制、可信的医疗系统界面

## 4. 色彩原则

- 主色建议使用低饱和蓝绿。
- 背景以浅色为主。
- 大面积背景避免高饱和紫、橙、红。
- 警示色只用于异常、风险、错误、重要提醒。
- 不使用强营销感渐变作为主要视觉语言。
- 色彩必须服务于阅读、分区和状态识别。
- 当前使用 Tailwind CSS 与既有 UI components；本文档只约束长期视觉原则，不定义或冻结具体 Tailwind token、class 和组件实现。

## 5. 布局原则

- 清晰分区。
- 信息层级明确。
- 临床工作流优先。
- 页面结构应围绕“患者施测、医护记录、医生复核、报告和临床运营”组织。
- 不堆叠过多卡片。
- 不使用复杂装饰性布局。
- 避免让视觉效果压过临床信息。

## 5.1 响应式与设备兼容基线

设计支持范围与代表性 CSS content viewport 如下；所有尺寸均指实际 `window.innerWidth × window.innerHeight`：

| 设备范围 | 代表性 viewport |
|---|---|
| 手机竖屏 | `390×844` |
| 大屏 Android 平板竖屏 | `800×1280` |
| 大屏 Android 平板横屏 | `1280×800` |
| 大屏 iPad 竖屏 | `1024×1366` |
| 大屏 iPad 横屏 | `1366×1024` |
| 紧凑桌面 | `1280×720` |
| 桌面大屏 | `1536×864` |

- 页面不得产生 document / main 全局横向溢出；Grid、Flex 和 Card 子项必须允许合理收缩。
- 宽表格允许在明确的局部容器中横向滚动，但不得撑宽整个页面。
- 多栏布局在窄屏下应自然收缩或切换为单列。
- Dialog、表单、主要按钮和错误提示必须保持可见、可聚焦、可操作。
- 图片、媒体证据、Canvas、连线、绘图和手写区域必须在大屏平板横竖屏下保持可用。
- 横竖屏或 viewport 变化不得静默丢失仍在 React 内存中的合法未提交草稿。
- 手机、标准触控设备和普通非触控电脑都不是彼此页面的简单缩小版。患者完整 MMSE / MoCA 主链以平板和具备触摸功能的电脑大屏为标准设备验收范围；手机只承担经逐步骤适配和验收的有限兼容，不要求完整患者施测流程全部可用。普通非触控电脑主要保证临床工作端的医护监管、医生复核和报告流程可用。

## 6. 字号与可读性

- 评估题目、患者信息、报告摘要、医生操作入口必须具备高可读性。
- 表格、表单、量表项需要足够行距。
- 避免小字号密集堆叠。
- 关键信息应优先可读，而不是优先节省空间。
- 患者端页面尤其要考虑老年用户或认知能力下降用户的阅读负担。

## 7. 交互与动效

- 少动画。
- 少复杂转场。
- 交互反馈要清楚、稳定、可预期。
- 不使用炫酷动效制造“科技感”。
- 临床工作端优先效率、异常可见和低操作负担。
- 患者施测终端优先理解、低压力和安全交接。

## 8. 装饰与视觉噪音控制

- 少装饰。
- 少大面积插画。
- 少强阴影。
- 少复杂渐变。
- 不使用娱乐化视觉元素。
- 不使用过度 SaaS 化的营销 Banner。
- 临床评估页面应保持克制、稳定、专注。

## 9. 信息重点

页面设计优先突出：

- 评估
- 记录
- 报告
- 医生工作流
- 患者认知评估状态
- 临床可追溯信息
- 评估进度
- 风险提示
- 报告生成与查看

## 10. 核心逻辑工作区与临床工作端设计基线

- 一期采用患者施测终端、临床工作端、临床运营与系统管理工作区三个逻辑工作区；它们可以复用同一前端应用、布局和工作流，不等于三套独立应用、微前端或强制角色分拆。知情者辅助信息采集不是第四套应用。
- 临床工作端在同一工作流内区分医护施测模式与医生复核报告模式。医生可以同时承担两种职责，不强制两个账号或互斥角色；由哪些现有固定角色承担具体职责，留给 WP-10.0 / WP-12 锁定。
- 医护施测模式优先支持患者 / 访视 / 量表选择、设备和语言准备、同设备交接或跨设备安全进入、当前步骤 / 进度 / 求助查看、动作观察、异常和影响因素记录，以及暂停、接管、纠正、恢复和终止。
- 影响因素采用结构化分类加必要补充说明的低负担呈现，至少能够覆盖感官、手部操作、语言 / 文化 / 教育、指令理解、疲劳 / 情绪 / 拒绝、环境、设备 / 网络和其他临床原因；本文不冻结枚举、字段或组件。
- 医生复核报告模式采用异常优先：优先呈现适用语音步骤的录音与转写修订、书写绘图、医护观察、异常步骤、缺失 / 不一致 / 低可信、人工评分、影响因素和无法完成原因。合同明确、无异常且无歧义的简单客观步骤可以汇总呈现和受控批量确认，不要求逐题机械点击。
- 医生必须能展开查看必要事实；修改要填写明确原因并形成留痕；最终进入提交、评分和报告链前必须显式整体确认。
- 临床运营与系统管理工作区继续使用最低充分页面或受控工具承载账号运营、患者 / 访视维护、临床任务入口、异常会话、报告输出和作废，不建设统计型 Dashboard 或复杂管理平台。
- 知情者信息由医护在患者或访视上下文中代录时，应清楚标识“来源：知情者”及关系、接触频率或了解程度等必要背景，并与患者作答、ItemResponse、量表得分和医生结论分区呈现；不要求知情者独立登录或家庭门户。

## 11. 患者施测终端设计基线

- 患者施测终端强调低压力、易理解、大字号、简单操作和隐私安全；采用一步一屏，每屏只有一个明确的主要操作。
- 使用大触控区、足够间距和尽量无需滚动的布局；触控一体机、触控显示器和大屏平板遵循同一低负担原则。手机仍只承担逐步骤验收后的有限兼容。
- 明确显示正在播放、正在录音、正在上传、等待医护和已完成等状态；只有步骤规则允许时才显示重播按钮。
- 始终提供清楚、容易触达的“请医护人员帮助”入口。患者不得自行跳题，除非步骤合同明确允许；不得以自动快速切题牺牲患者理解或医护观察。
- 不使用复杂导航、表格、密集表单、游戏化积分、答案提示或诊断暗示，不展示分数、报告、医生意见和其他患者信息。
- 患者施测终端应根据施测步骤语音播报当前题目内容和施测指导语。每个步骤分别确定文字是否显示、是否播报、自动播放或患者主动播放、是否允许重播、重播次数或条件、播放完成前能否作答，以及中断和失败处置；不得使用一个全局规则控制全部步骤。
- 题目内容、施测指导语、影响测量条件的刺激和普通操作 / 状态提示必须分层。普通题目与指导可以采用经确认的录音或运行时 TTS；词语、数字串、复述句、警觉性刺激等采用版本化且受控的音频。文字显示必须服从题目规则，视觉任务只播报必要指导且不得泄露答案；禁止把页面全部文本交给全局 TTS 无差别朗读。
- 正式施测前提供最低充分的准备：设备和浏览器提示、屏幕方向及有效区域确认、音量试听、适用时的麦克风试听、触摸或书写试操作、施测语言确认、明显影响因素记录，以及至少一个不使用正式刺激的不计分练习。医护确认患者理解后才能开始正式施测；练习不得进入 ItemResponse、评分、报告或正式计时 / 重播事实。
- 同设备从医护工作模式进入患者模式后，后退、刷新、历史记录和普通导航均不得进入临床工作端；患者模式只显示当前施测所需的最少身份信息。完成、终止或超时后清除患者可见内容，结束页只提示完成并要求交还设备；返回临床工作端需要医护显式安全解锁或重新验证，具体实现不由本设计基线预设。

## 12. 报告与评估结果设计基线

- 报告页面优先清晰、可读、可追溯。
- 评估结果不能用夸张颜色制造诊断暗示。
- 风险提示必须克制、准确、可解释。
- 不把系统结果写成最终医疗诊断。
- 报告视觉应适合医生查看、打印或导出。

## 13. 与 ReviewX 的关系

- ReviewX 仅作为工程结构、配置经验和组件治理方法参考。
- 不继承 ReviewX 的视觉风格。
- 不继承 ReviewX 的颜色体系。
- 不继承 ReviewX 的页面布局。
- 不继承 ReviewX 的业务文案。
- 不继承 ReviewX 的项目评审管理后台气质。
- CogMemory AD 与 ReviewX 必须保持前端视觉隔离。
- 后续迁移 ReviewX 前端 `app` / `src` 时，必须按 CogMemory AD 设计基线重构视觉表现。

## 14. 禁止事项

- 不照搬 ReviewX 页面视觉。
- 不照搬 ReviewX 管理后台气质。
- 不使用高饱和大面积装饰色。
- 不使用强营销感视觉。
- 不用动画替代清晰信息结构。
- 不让装饰影响评估题目、患者信息、报告结果的阅读。
- 不在 UI 中展示真实患者隐私样本。
- 不把评估结果设计成最终诊断结论。

## 15. 后续维护规则

- 新增页面、组件、布局、样式前，应先检查本文档。
- 当前已实现页面与组件继续遵循本文档；具体实现事实由 frontend snapshot、component map 与代码维护。
- 如后续实际产品风格调整，应先更新本文档，再改页面和组件。
- `handoff-frontend-component-map.md`、`handoff-frontend-route-map.md`、`handoff-frontend-testing-playbook.md` 应与本文档保持一致。
- 七个正式 viewport 若调整，必须同步更新 `handoff-frontend-testing-playbook.md`。
- 本设计基线定义“必须适配什么”，`handoff-frontend-testing-playbook.md` 定义“如何验证”；测试执行、结果判定和证据归档细节只在 testing playbook 维护。
- Codex 后续执行前端页面或组件迁移任务时，必须把本文档作为视觉基线。
